## 这是什么问题

班组每天三次点检，靠老师傅拿手电筒看。问题不在"看不出来"，在"看不出来之后什么都不会留下"。

| 场景难点 | 我们的处理方式 |
|---|---|
| "我看着不对劲，但说不清哪不对" | 拍照后给出异常类型和位置框，把感觉变成可指认的东西 |
| "上周好像也这样" | 同一设备的历史点检按时间线排开，差异直接标出来 |
| "报告是下班后补的" | 点检完成即生成报告，不用回头补 |

## 功能是什么

**手机端（点检工人）**

- **拍照点检**：对着设备拍一张，30 秒内返回异常类型、位置框、建议处置
- **一键复检**：对上次标记过的异常位置，直接拍同角度对比
- **离线暂存**：地下车间没信号也能点检，回到地面自动同步

**PC 端（班组长）**

- **点检报告台**：按班组/设备/日期筛，异常项按严重度排序
- **历史对比**：同一设备历次点检并排，新出现/已消除的异常高亮
- **导出**：一键出 PDF，含照片、时间戳、复核人

## 三个核心设计

### 1. 异常定位优先于异常分类

工人不需要知道"这是渗油还是漏油"，他需要知道"是这儿，去处理"。所以模型输出的第一优先级是位置框，类别只作为辅助标签。

**我们没有做**多缺陷同时分割——一次只框最严重的一个，宁可漏报也不误报。相关源码：[`api/vision/locator.py`](api/vision/locator.py)

### 2. 复核人机制代替自动归档

所有 AI 识别结果默认进入"待复核"，必须由人确认才进正式记录。这不是降级，是点检记录的法定要求。

**我们没有做**全自动闭环。相关源码：[`api/workflow/review.py`](api/workflow/review.py)

### 3. 本地推理，照片不出车间

现场网络不可靠，且设备照片在部分产线属于敏感数据。识别模型跑在车间内网的一台机器上。

**我们没有做**云端识别，也不支持跨车间联邦。相关源码：[`api/vision/runtime.py`](api/vision/runtime.py)

## 怎么跑

```bash
# 1.
git clone https://github.com/example/checkmate.git && cd checkmate
# 2.
cp .env.example .env    # 必填项在注释里，主要是模型文件路径
# 3.
docker compose up -d    # 首次启动会拉取模型，约 8 分钟
```

## 边界

- **没做的**：不做设备预测性维护（本项目的定位是"记录现状"，不是"预测故障"）；不做多缺陷同时分割
- **没验证的**：只在 3 个车间、6 类设备上实测；夜间低光照环境下准确率未单独评测；iOS Safari 的相机兼容只测到 iOS 16
- **会崩的**：单张照片超过 12MB 会上传失败；并发超过 8 路点检时队列明显变慢；车间内网断网超过 30 分钟，同步会失败需要重新登录

## 常见问题

| 问题 | 检查顺序 |
|---|---|
| 照片传上去了但一直转圈 | 先看 `.env` 里模型路径是否存在 → 再看 `docker compose logs api` 有没有加载成功 → 确认照片小于 12MB |
| 识别结果全是"无异常" | 确认没走错端口（`/m` 是手机端，`/` 是报告台）→ 确认 `materials/samples/` 里的照片能复现 → 换一张清晰的 |
| 换了新模型但结果没变 | 模型文件是按路径加载的，改 `.env` 后要 `docker compose restart`，光 `up -d` 不会重载 |
| PDF 导出缺照片 | 检查 `materials/uploads/` 目录权限，容器内是 1000:1000 |
